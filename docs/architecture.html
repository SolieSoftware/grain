01The failure this exists to prevent

Measured on the loaded database, 17 Aug 2026

A metric only means something at the grain of the table it aggregates. Join that table to anything with higher cardinality and its rows are replicated, so the sum silently multiplies. Grain is nowhere in the schema — a foreign key records that two tables relate, never what one row means — so an agent writing SQL from a schema dump cannot reason about it.

Two things make this worse than it first looks. The offending join is not itself wrong — the same path is correct for a metric that lives at the finer grain, so no rule about joins can catch it. And the inflation factor isn't the average line count you might divide by to sanity-check it: it is weighted by the very quantity being measured, since larger invoices carry more lines. Here that lifts it from 5.44 to 8.95.

Spec 01Grain-aware aggregation
Plan
Every metric declares a grain; every link declares a cardinality. Before compiling, compare the metric's grain against the finest grain the resolved path reaches. Three outcomes — aggregate inline, rewrite as aggregate-then-join at the metric's own grain, or refuse. Never emit a query whose correctness depends on the current data.
Lives in
engine/grain.py decides · engine/compile.py emits · domains/*/ontology.yaml declares
Verified by
  • Unit, no database: QuerySpec → expected SQL for each outcome
  • Integration: revenue and invoice_total both return 2328.60 at their own grains
  • Integration: the fanned path refuses — 20848.62 must be unreachable through any spec
Decided
R2 ✓ Rewrite and surface it — refusal is not the answer where a correct rewrite exists. Each rewrite appends to a rewrites[] record on the result naming the metric, the fan-out edge that forced it, and the strategy applied. A rewrite the reader cannot see undoes the point of returning compiled_sql.

02The shape

Four layers · only the middle two are ours

The library is the product. Every other surface — MCP, CLI, your own chat harness — is a thin adapter over it, and engine/ imports none of them. The falsifiable test of this architecture: pointing grain at a second database must not change a line under engine/.

Spec 02Keeping the boundary honest
Plan
The library is the product. engine/ imports no adapter and no domain module — domain packs are data plus generated code, located by path at startup rather than imported by name. Adapters translate transport to QuerySpec and nothing else.

03Where a request can die

Every failure is caught before the database, and names its own fix

The agent reads errors and retries, so an error that only says no wastes a turn. Each stage raises a typed failure carrying the legal alternative — which is what lets the loop converge instead of drift.

Spec 03Errors as an interface
Plan
One typed exception hierarchy. Every error carries the offending name and the legal alternatives — nearest valid names, what does connect two objects, the safe reformulation of a metric. No error may be raised that only says no. All of them are raised before a database session is acquired.
Lives in
engine/errors.py defines · raised from resolve.py and grain.py
Verified by
  • One unit test per error type asserting the message names an alternative that is itself valid — the suggestion has to resolve, or it wastes the retry it was meant to save
  • A test asserting no connection is opened on any failure path
Decided
R4 ✓ Keep five stages. The separation is earning its keep in error attribution — each stage owns a distinct failure class, which is what lets an error name a specific fix rather than a general one.

04The grain decision

The one piece of reasoning the database cannot do for us

Run per requested metric. Cardinality comes from the ontology, declared rather than inferred — a foreign key proves many_to_one, but nothing in the schema reliably proves the reverse.

Spec 04The analysis pass
Plan
A total function: every (path, metric) pair lands in exactly one outcome, from declared cardinality alone — no data access, so the verdict cannot drift as rows are added. Runs per metric, so a query with metrics at three grains gets three verdicts and three subqueries. Additivity is computed alongside and is orthogonal: a response can be aggregate-then-join and non-additive at once, which is exactly what revenue by playlist is.
Lives in
engine/grain.py
Verified by
  • A branch-per-row truth table — every path through the diagram gets a unit test
  • Chasm branch tested against Track → InvoiceLine + Track → PlaylistTrack. Not Employee, which returns 0 rows and would pass vacuously
  • A property test that the function is total: no input reaches the end without a verdict

05The Chinook ontology

The first domain pack — chosen because it forces every construct

Spec 05Declaring a domain
Plan
One YAML file per domain: object types (which may span tables via named outer joins), link types (direct · through · recursive, each with explicit path and declared cardinality), and metrics carrying grain and ai_context. Cardinality is declared, never sniffed — inferring it from data infers a schema property from an accident of the current rows.

06How it gets settled

Two arms, one harness — everything fixed except the toolset

The claim is narrow and stated in advance: the ontology should win on grain correctness and deep traversal, and roughly tie everywhere else. Raw text-to-SQL is expected to tie on the single-hop half. If arm A doesn't win on the traps, the design is wrong.

Spec 06Settling the claim
Plan
25 hand-verified questions written before any tuning — roughly 12 single-hop, 13 multi-hop, of which 3–4 are deliberate fan-out traps and 2 are recursive. Two MCP servers under one client, identical guard. Result pre-registered: arm B ties on the single-hop half; arm A must win on the traps or the design is wrong.
Lives in
tests/eval/ · scorer calls the library directly, not through MCP, so scoring stays deterministic
Verified by
This is the verification. Scored on exact-answer accuracy, turns-to-answer, and silently-wrong numbers counted separately from visible failures — collapsing those two into one accuracy column would hide the entire point.
Decided
R3 ✓ Accepted as a permanent limit, not a gap. Every arm-A failure is classified before it is counted — grain error (the engine), selection error (ai_context quality), traversal error (the link vocabulary) — and reported in separate columns, so bad prose can never masquerade as a failure of the grain layer.

08Decisions taken on review

17 Aug 2026 · five settled, one deferred

  1. R1 ✓

    Join conditions: structured pairs

    on: [{from: track.album_id, to: album.album_id}] rather than an expression to parse. No grammar to write and no parser to get wrong; a malformed pair fails at load rather than mid-query. Composite keys fall out as a longer list, and the shape matches Ossie's from_columns/to_columns, so the exporter stays mechanical. Cost is verbosity — the right thing to trade.

  2. R2 ✓

    Rewrite, and surface the rewrite

    Where a correct rewrite exists, refusing is the worse answer — but the caller still has to know the shape of their query changed. Each rewrite appends to a rewrites[] record naming the metric, the fan-out edge that forced it, and the strategy applied. Auditability is the reason compiled_sql is returned at all; an invisible rewrite would undo it.

  3. R3 ✓

    Metric selection: a permanent limit, not a gap

    This one doesn't get solved. It isn't really an agent defect — people are imprecise about what they mean, and vocabulary and explicit communication aren't most users' strong suit, so the gap between what was asked and what was meant never fully closes. grain guarantees the answer is computed correctly; it does not guarantee the right question was asked. ai_context narrows the gap and is expected to reduce these errors, not eliminate them — so they're counted in their own column, where they can't masquerade as a failure of the grain layer.

  4. R4 ✓

    Keep five pipeline stages

    The separation is earning its keep. Each stage owns a distinct failure class, which is what lets an error name a specific fix rather than a general one.

  5. R5 ✓

    Keep explain

    Worth the turn it costs, particularly during bring-up: it makes the compiled SQL and the grain verdict visible before anything executes. Whether the agent reaches for it unprompted stays worth measuring — but as information about the affordance, not a reason to drop it.

  6. R6

    Second domain — deferred

    Picked once the design is finished. Worth keeping in view: the milestone-8 architecture test is only meaningful if the engine hasn't already been quietly shaped around Chinook, so the longer this waits the weaker the test gets.

Also settled

  1. S1 ✓

    Non-additivity is announced twice, asymmetrically

    The result flag is authoritative — computed for the actual query, so it can't go stale. But arriving only there means the agent learns after asking, and one that skips result metadata presents a clean 12-row table whose column silently sums to 5738.28 instead of 2328.60. Every number in it is correct: the wrong number was prevented in the SQL and reintroduced at the point of reading.

    Publishing it per (metric × dimension) pair would grow multiplicatively with the ontology. So describe_ontology states the rule instead — a metric grouped by a dimension reached through a many_to_many link is non-additive — one sentence, total coverage, unchanged at 200 tables. The agent already sees the cardinalities; it only lacked the implication.

  2. S2 ✓

    Progressive disclosure — not a problem yet

    Closed rather than deferred. Revisit only when a domain's ontology stops fitting comfortably in context. The S1 resolution above was chosen partly so it doesn't bring that day any closer.

Not in v1 — deliberately

Writeback and Actions · RDFS/OWL inference · entity resolution · vector search · multi-database federation · caching · row-level permissions.

And specifically: provenance, knowledge_level, bitemporal validity and contradiction handling. Those are the Knowledge Graph Engine's core machinery, and they're absent here because one trusted database means one provenance. That omission is the seam where the two projects would converge.
