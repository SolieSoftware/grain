Names to SQL

Two modules stand between a typed request and a statement the database will run. resolve.py turns names into structure. compile.py turns structure into SQL. Neither one is allowed to do the other's job — and that separation is what makes the answer checkable.

Traced live · chinook v1.4.5, PostgreSQL 17 8 specs executed through the real pipeline 241 tests passing at time of writing

Every value on this page was read off the objects the real functions produced — resolve(), analyse(), compile_query() — with Scope.register and Scope.column instrumented to record the order they were actually called in. No example here was written by hand.

00

The problem both modules exist to solve

A metric means something only at the grain of the table it aggregates. Join that table to anything with higher cardinality and its rows are replicated — so the sum counts the same money more than once.

Grain is not in the schema. A foreign key records that two tables relate, never what one row means. So the ontology holds that one fact, and these two modules are what turn it into a statement.

01

Five stages, and what crosses each boundary

resolve.py is the widest gate and the cheapest failure. Everything it rejects is decidable from the ontology, so a typo costs a validation error rather than a query. compile.py is the opposite: by the time control reaches it, every judgement has already been made, and its job is to emit exactly what was decided.

02

resolve.py — names into structure

The input is a QuerySpec whose every string must name something the ontology declares. The output is a ResolvedQuery: the same request with every name replaced by the thing it names, and a walked path of edges.

Take the flagship spec. Here is what went in, and what came out — traced, not illustrated:

Notice what the resolver added that the spec did not carry: the cardinality of each hop, the physical column behind country, its nullability, whether it is declared unique, and the grain of the metric. Those five facts are what every later decision is made from.

The traverse walk is a chain, not a graph

resolve keeps a current object and requires each hop to start where the last one ended: 

current = root
for hop in spec.traverse:
    link = onto.links[hop.link]              # else UnknownName
    if link.from_ != current.name:            # else NoPath
        raise NoPath(current.name, link.to, links_from(current.name))
    if hop.max_depth is not None:
        link = link.model_copy(update={"max_depth": hop.max_depth})
    path.append(Edge(link=link, from_object=current, to_object=target))
    current = target

Three things are doing real work here. The chain rule makes a branching path unrepresentable — you cannot go out to invoices and back to a customer's support rep in one spec — which is precisely why the engine needs no "chasm trap" detection. The model_copy gives the hop a private copy of the link with its own max_depth, so overriding depth on one hop cannot mutate the shared ontology. And the Edge triple records from and to alongside the link, so later stages never have to re-derive which object a hop departed from.

Two kinds of dotted name, which mean different things

the consequence, measured

"invoice_total where the invoice is over 10" reads as a row filter and is not one. The population reading returns 2328.60 over 412 invoices; the row reading would return 942.32 over 64. Same spec, and the difference is a factor of 2.5 — which is why the rule is published rather than left to be inferred.

edge_index: the field that makes a column mean one row

A qualified group key resolves to a ResolvedProperty carrying edge_index — the position on the path at which the column is read. This exists because a column reference alone is ambiguous: employee.last_name is one column, but a query that walks Employee_Manager has employee in scope twice, as the employee and as the ancestor. Same column, two different rows.

A qualified key names a link, not a hop. So walking the same link twice makes the key unanswerable, and the resolver says so rather than guessing: 

AmbiguousGroupKey: Group key 'Employee_Manager.last_name' names 'Employee_Manager',
which this query traverses 2 times (hops 1, 2). A qualified key names a link,
not a hop, so it cannot say which one is meant.

Everything the resolver refuses

All of it decidable from the ontology, all of it naming a next move. The messages below are verbatim from the traced run.

ErrorRaised whenWhat it names
UnknownName An object, link, property, metric or order_by key the ontology does not declare Up to 3 close matches by edit distance — "Unknown property of Customer 'contry'. Did you mean: country, city?"
NoPath A hop whose from is not where the walk currently stands Every link that does leave the current object
GroupKeyNotOnPath A qualified key naming a link that is not traversed "add the Employee_Manager hop to traverse"
AmbiguousGroupKey A qualified key naming a link traversed more than once The hop numbers it could have meant

Two quiet correctness details

Duplicates are collapsed, not rejected. group_by=["country","country"] means what asking once means, and a caller assembling a spec programmatically does it often. Left in, it becomes two identically-labelled SELECT columns and two identically-aliased subqueries, which SQLAlchemy rejects mid-compile — a crash on a request whose meaning was never in doubt. _unique() keeps the first occurrence, so the caller's own column order survives.

order_by is validated against what the query emits. A key that names neither a group key nor a requested metric could never be honoured, so it is a typed error at the door. This one is recent: the field was accepted and never read for the whole build, and with limit defaulting to 100, "top 10 countries by revenue" returned ten arbitrary countries — omitting USA, the largest at 523.06 — correctly computed, with nothing to say the result was partial.

03

The verdicts, in between

compile.py cannot be read without this stage, because it consumes its output. analyse() asks one question per metric: where does this metric's grain enter scope, and what happens to its rows after that?

Three specs, same database, three different verdicts. All traced:

SpecMetric @ grainPrefixDownstreamVerdictsubquery_edgesadditive
A revenue by country revenue @ invoice_line both hops — inline 2 true
B invoice_total by country invoice_total @ invoice Customer_Invoices Invoice_Lines aggregate-then-join 1 true
D headcount by ancestor employee_count @ employee — (root grain) Employee_Manager inline 1 false

A and B are the same path and differ only in which metric was asked for. D is the interesting one: it has a fanning edge downstream of its grain, which by the rule above should force a rewrite — yet it came back inline.

The reason is the one refinement to the core rule. A fanning edge replicates the metric's rows, and the rewrite exists to stop those copies being summed together. But the group key Employee_Manager.id pins one employee at that hop, so each copy lands in a different ancestor's group and appears exactly once inside it. Correct per group, meaningless as a total — hence additive: false. It is the mirror image of "revenue by playlist", which the engine already answered that way.

deliberately narrow

The pinning key must sit at the fanning edge's own position. A key further along determines the row at that edge only when every edge in between is functional in reverse. The counterexample: Playlist → Playlist_Tracks (m2m) → Track_Album (m2o) grouped by a unique album key — one album does not determine which track, so a playlist holding two tracks from one album appears twice inside that album's group. The wider rule is a non-goal until something measures that it is needed.

When neither applies, the query is refused with the alternatives named. Verbatim from the trace, for a spec identical to D except that it groups by the ancestor's name: 

KeyBeyondGrain: Metric 'employee_count' is at 'employee' grain and must be
pre-aggregated here, but the group key 'Employee_Manager.last_name' lies beyond
that grain across 'Employee_Manager', which fans out. Carrying the key into the
pre-aggregate would replicate the metric's own rows.
Alternatives: drop the 'Employee_Manager.last_name' group key, use a metric whose
grain reaches 'Employee_Manager.last_name', remove the Employee_Manager hop.
04

compile.py — structure into SQL

One idea runs through the whole module: a column reference is not enough to say which row is meant. So every position on the walked path gets its own FROM element, and a property is read off the element for its position. That is what Scope is.

Scope, traced from the recursive spec

A table is aliased only when its name is already in scope. That restraint is load-bearing twice over: a query that never revisits a table compiles to byte-identical SQL to before Scope existed — which is what the provenance guarantee rests on — and metric expressions are raw SQL naming real tables, so aliasing everything would break them silently.

FROM first, columns last

compile_query builds in an order that looks odd until you see why: it selects the root's columns as a placeholder, assembles the whole FROM clause, and only then replaces the columns clause with with_only_columns. 

scope.register(None, root.primary, root_table)        # position "root"
stmt = select(root_table).select_from(root_table)       # placeholder columns
stmt = _apply_object_joins(stmt, scope, None, rq.root, root_table)
stmt = _apply_path(stmt, scope, rq)                    # every hop, in order
stmt = _apply_filters(stmt, scope, metadata, rq)

group_cols = [scope.column(rp).label(rp.name) for rp in rq.group_by]   # NOW resolvable
stmt = stmt.with_only_columns(*group_cols, *inline_cols)

A qualified group key cannot be resolved until the hop that brings it into scope has been applied. So the FROM clause has to exist before the SELECT list can be written — the reverse of how one reads SQL.

A recursive edge used to skip object joins, on the reasoning that "that object's spanned tables are already joined". True while the CTE joined each row to its own hierarchy row — the target was the source row. Now that the target is the ancestor, reusing the employee's department would report it under the manager's name: the same wrong-entity bug, one table further out.

Dotted filters become EXISTS — and where that went wrong

Every dotted filter compiles to EXISTS, fanning or not. Across a fanning hop a join would return one row per matching child and multiply the parent. Across a non-fanning hop there is no multiplying risk, but the target table is only in FROM if the same link also appears in traverse — and a plain WHERE on an unjoined table becomes an implicit, unconditional cartesian product that SQLAlchemy adds silently. EXISTS carries its own join condition, so that is unconstructible rather than merely unlikely.

The subtlety is which table the subquery is built from. It must be the link's target object, never the table the filtered property happens to sit on — those differ whenever the property is reached through one of the object's own joins:

wascartesian product
WHERE EXISTS (
  SELECT 1
  FROM genre, track
  WHERE album.album_id = track.album_id
    AND genre.name = 'Jazz')

-- no track.genre_id = genre.genre_id
-- means: "this album has any track,
-- and some genre called Jazz exists
-- anywhere"
traced nowspec C
WHERE EXISTS (
  SELECT 1
  FROM track
  LEFT OUTER JOIN genre AS genre_1
    ON track.genre_id
     = genre_1.genre_id
  WHERE album.album_id = track.album_id
    AND genre_1.name = 'Jazz')

The via join is applied inside the subquery and the predicate binds to the joined column. Four specs in the shipped ontology hit the broken shape; it returned 347 of 347 albums for a filter that matches 13, and a Rock-only album passed a Jazz filter. It now returns 13. The outer join is kept rather than made inner because it stays faithful to the declaration — an is_null filter on a left-joined property means "reached this row, and it has no match", which an inner join would make unsatisfiable.

The correlated side is read from metadata rather than from a Scope, and that is safe for a specific reason: a dotted filter is always anchored on the root object, and the root's own tables are the one thing Scope never aliases — they are registered first, so nothing can collide with them.

Aggregate-then-join, and its two Scopes

When a metric must be pre-aggregated, the subquery starts at the root and walks outward — applying mp.subquery_edges edges, which is the longer of "the prefix reaching the grain" and "far enough to carry every group key". It gets its own Scope, because it is an independent FROM: a table aliased there has nothing to do with the outer query's element for the same table.

The instrumentation caught both scopes in spec B — two distinct objects, registering different amounts of the same path:

The subquery stops at hop1. Applying Invoice_Lines there would replicate the invoice rows inside the very subquery built to stop that happening — the same bug, one level down. Positions are full-path indices in both, so a qualified group key resolves to the same object either side.

traced sqlspec B — invoice_total over a fanning path
SELECT customer.country AS country,
       invoice_total_at_invoice.invoice_total AS invoice_total
FROM customer
  JOIN invoice ON customer.customer_id = invoice.customer_id
  JOIN invoice_line ON invoice.invoice_id = invoice_line.invoice_id
  LEFT OUTER JOIN (
      SELECT customer.country AS country, sum(invoice.total) AS invoice_total
      FROM customer JOIN invoice ON customer.customer_id = invoice.customer_id
      GROUP BY customer.country
  ) AS invoice_total_at_invoice
  ON customer.country IS NOT DISTINCT FROM invoice_total_at_invoice.country
GROUP BY customer.country, invoice_total_at_invoice.invoice_total

24 groups totalling 2328.60 — the correct figure, over a path whose naive form gives 20848.62. Reported as aggregate_then_join, forced_by: Invoice_Lines, reason: "Invoice_Lines is one_to_many".

Two details in that statement carry more weight than their size suggests.

IS NOT DISTINCT FROM, not =. customer.country is nullable, and NULL = NULL is NULL, not true — so under plain equality every row whose key is NULL misses its own group. A silent undercount, of exactly the kind this engine exists to make unreachable. The operator is chosen per key from three independent sources, with the database authoritative: a hand-written nullable: false over a genuinely nullable column cannot weaken it.

No coalesce(…, 0). The outer key set is a subset of the subquery's — both start at the same root under the same filters, and the outer's extra edges are inner joins, which can only drop keys, never invent one. So a miss is not "a group with no facts"; it is a key that failed to match a key it should have matched, and the only way that happens is a broken comparison. A zero there would repaint that as a plausible number. NULL leaves the fault visible.

06

The invariants that keep the two apart

resolve.pycompile.py
Knows about The ontology The ontology, reflected MetaData, and the plan
May decide Whether a name exists and whether a path is walkable Nothing about grain — every verdict arrived already made
Reads data Never Never — it emits a statement, it does not run one
Failure means The request named something that does not exist, or a path that does not connect The plan could not be rendered — a narrow, enumerable set

One honest wrinkle in that last row. compile.py's docstring says it "decides nothing", and it very nearly doesn't — but it still raises in two places: when only rewritten metrics are present with no keys to rejoin them on (there is no correct query to emit, so it refuses rather than guessing), and when a spec asks for no group key and no metric at all. Both are structural, not grain judgements. Worth knowing before trusting the docstring literally.

The reason the separation is worth this much care is that four of the five critical defects found in review produced correct-looking SQL. A statement that compiles, runs, and returns plausible rows is not evidence of anything. What makes the answer checkable is that each stage can only be wrong in its own way — and that the compiled SQL rides back on every result, byte-identical to what explain() showed, because planning reads only the spec and the ontology.
