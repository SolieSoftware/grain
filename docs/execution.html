01Before any of this: where the spec comes from

Nothing in this repository turns English into a QuerySpec. There is no model call, no prompt, no parser — the dependencies are SQLAlchemy, psycopg, pydantic and PyYAML. The translation happens inside whichever agent holds the MCP tools, and the repo's whole contribution to that step is describe(): it publishes the vocabulary and the rules the agent has to respect, in place of a DDL dump.

Three things follow from that division of labour.

The CLI is a peer, not a stage. grain query --spec '{…}' takes the JSON already written, parses it at cli.py:51, and calls the same api.py. It does not go through the MCP server, and the MCP server does not go through it — the two adapters converge on the library, never on each other.

Nothing constrains the agent at generation time. Both MCP tools declare spec: dict, so the published input schema is {"type": "object", "additionalProperties": true} — the agent is not even schema-bound on field names, let alone on which objects and metrics exist. QuerySpec's own schema does close the field set and enumerate the nine filter ops; it is simply never handed over. Every name stays a bare string until resolve checks it against the ontology.

A refusal is a turn in a loop. That is why every error carries alternatives: NonAdditiveRefused names group_by … id, FanOutRefused names the hop to add. The agent repairs and calls again — one more round trip, not a dead end.

02The whole path, at once

The agent emits a QuerySpec and nothing else — no SQL, no Python. Everything below happens inside Grain.query(), which is 12 lines long because every decision has already been given somewhere to live.

03Stage by stage, with what kills it

Each stage is given one job, one input type and one set of typed exits. The “can die with” column is the interesting one: a refusal here always carries alternatives, because an error that only says no costs the agent a turn and teaches it nothing.

Validate — QuerySpec.model_validate (spec.py)

Reads

  • The agent's JSON, nothing else
  • ConfigDict(extra="forbid") on every model

Decides

  • Shape only: object, filters, traverse, group_by, metrics, order_by, limit
  • op:"in" needs a sequence; op:"is_null" takes no value
  • limit defaults to 100, None means no LIMIT clause

Can die with

  • ValidationError — a misspelled field is rejected at the door rather than silently ignored

Resolve — resolve() (resolve.py)

Reads

  • The ontology's objects, links, properties, metrics
  • No database, no rows

Decides

  • Walks traverse into a path of Edges, checking each link departs from the object it lands on
  • Binds each group key to a position: None for the root, i for the object hop i lands on
  • Dotted filters resolve to one hop and become EXISTS — they change the population, not the row
  • De-duplicates keys and metrics; validates every order_by key is actually emitted

Can die with

  • UnknownName — with difflib suggestions
  • NoPath — link does not start here
  • GroupKeyNotOnPath — qualified by a link you did not traverse
  • AmbiguousGroupKey — that link appears twice on the path

Analyse — analyse() (grain.py)

Reads

  • Declared cardinality on each edge
  • Each metric's declared grain table
  • Whether a group key is declared unique

Decides

  • path_to_table: the shortest prefix that brings the grain into scope
  • Fanning edges downstream of the grain force aggregate_then_join; edges upstream are harmless
  • A fanning edge pinned by a unique key at its own position stays inline — its copies land in different groups
  • additive: false when any edge in the prefix is effectively many_to_many
  • subquery_edges: how far a pre-aggregate must walk to carry every key

Can die with

  • FanOutRefused — grain not on the path; names the hop to add
  • NonAdditiveRefused — non-additive without a key that identifies one row
  • KeyBeyondGrain — the key can only be reached across a fanning edge

Compile — compile_query() (compile.py)

Reads

  • The resolved query, the plan, the reflected MetaData

Decides

  • Scope holds one FROM element per position, aliasing a table only when that name is already in scope (employee_hop1)
  • FROM first, columns second — a qualified key cannot resolve before its hop is applied
  • A recursive link becomes a depth-bounded WITH RECURSIVE ancestor walk carrying __grain_start
  • Rewritten metrics become a correlate-free subquery LEFT JOINed back on the keys, never coalesce(...,0)
  • Same spec in, byte-identical SQL out — nothing here reads data or the clock

Can die with

  • FanOutRefused — only rewritten metrics and no key to rejoin them on
  • GrainError — a query that asks for neither a key nor a metric

Execute — execute() + guarded_connection() (execute.py, guard.py)

Reads

  • The compiled Select, the GuardConfig
  • The database — for the first time since load

Decides

  • Pins READ COMMITTED, then begin() explicitly, so SET LOCAL statement_timeout has a transaction to bind to
  • Fetches row_cap + 1 rows, so “complete” and “truncated at exactly the cap” stay distinguishable
  • Always rollback() — the connection is read-only by construction
  • Column labels come off cursor.keys(), not from the caller's metric order

Can die with

  • GuardTripped("row_cap", 10000)
  • Postgres cancelling the statement at 10 s

What comes back. Result carries rows and columns, plus the four things that make the answer auditable: compiled_sql (the exact statement that ran), rewrites (what the engine changed and which edge forced it), additive with non_additive_reason, and limit_reached. A metric that matched no group comes back None, never 0.

04The one decision the database cannot make

Everything above is plumbing around this: where a metric's grain sits relative to the fanning edges on the path. Same two hops, two metrics, two different verdicts — decided from declared cardinality alone.

The rewrite computes the metric at its own grain in a correlate-free subquery and joins the answer back on the group keys. The outer query keeps the fanned rows — the caller asked to traverse there — but the metric no longer sees them.

The refusal, in full — this is what the agent reads

NonAdditiveRefused: Metric 'revenue' is reached through 'Playlist_Tracks',
which is many_to_many, so one 'invoice_line' row belongs to more than one group.
The group_by keys (name) do not identify one row of the object they name, so two
rows sharing a value merge into one group and everything reachable from both is
counted twice inside it.
Alternatives: group_by a property that identifies one row: id.

Yes — and the pipeline's shape is what makes it cheap. Because resolve, analyse and compile read declarations only, most of the engine is testable as a pure function from spec to SQL string. Both runs below are from this working tree, today.

Three test styles doing different work

Measured anchors. test_revenue_at_line_grain_is_2328_60 and test_the_inflated_figure_is_unreachable assert numbers, not statements. Four of the five critical defects produced correct-looking SQL, so a test that inspects a statement would have passed on all of them.

Defect anchors. One test per fixed defect, each asserting the number the defect got wrong — 13 Jazz albums not 347, playlists 1 and 8 separated at 2 107.71 each, the top countries by revenue actually being the top countries.

The architecture test. test_boundary parses every file under engine/ and fails if one imports a domain, in any import form — the second-domain claim, enforced continuously rather than checked once.

Reproducing the traces on this page

set -a && . ./.env && set +a          # GRAIN_DATABASE_URL

# every stage, printed, for one spec
uv run python - <<'PY'
import os
from sqlalchemy import create_engine
from grain.engine.api import Grain
from grain.engine.spec import QuerySpec, Hop
from grain.engine.resolve import resolve
from grain.engine.grain import analyse
from grain.engine.compile import compile_query, sql_text
from grain.domains.chinook import CHINOOK_DIR

g = Grain.load(CHINOOK_DIR, create_engine(os.environ["GRAIN_DATABASE_URL"], future=True))
spec = QuerySpec(object="Customer", group_by=["country"], metrics=["invoice_total"],
                 traverse=[Hop(link="Customer_Invoices"), Hop(link="Invoice_Lines")], limit=None)

rq = resolve(spec, g.ontology)
plan = analyse(rq)
print([e.link.name for e in rq.path])
print([(mp.metric.name, mp.strategy, mp.forced_by, mp.subquery_edges) for mp in plan.metric_plans])
print(sql_text(compile_query(rq, plan, g.metadata)))
r = g.query(spec)
print(len(r.rows), sum(x[1] for x in r.rows), r.additive, r.limit_reached)
PY

# compiles and reports the verdicts without running anything.
uv run grain explain --spec '{"object":"Customer","group_by":["country"],

What is not testable yet

Two things, and they are the project's actual claims rather than details:

The comparison that would justify the engine has no test to run. There is no golden question set and no ablation against raw text-to-SQL, so “an agent with grain is more correct than an agent with a schema dump” is unmeasured. That needs a fixed set of questions with known answers — a harness this repo does not have, not a test it is missing.

Portability is asserted by one AST test and one domain. test_boundary proves engine/ imports no domain; it cannot prove a genuinely different database needs no engine change. Only a second domain pack does that.
